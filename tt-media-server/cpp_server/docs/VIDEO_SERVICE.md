# Video service

A job-based video generation HTTP service in `cpp_server` (text-to-video, and
image- or reference-conditioned video for the models that take it). It mirrors the API of the
Python `tt-media-server` video endpoints: a request creates a job, the video is
generated by a runner that owns the device (on a thread of the server process, or in
a separate worker process, see [Execution modes](#execution-modes)), and the client
polls the job and downloads the mp4 when it is done.

Status: the service is tested on a mock runner (no device) and on a T3K with
Wan2.2. See [Tests](#tests) and [Known limitations](#known-limitations).

## Execution modes

| | In process | Worker process |
|---|---|---|
| chosen when | exactly one `DEVICE_IDS` group (the usual T3K launch, also with several chips in the group) | two or more `DEVICE_IDS` groups, one process per group |
| runner lives in | a thread of the server process | one forked process per group (`--worker <i>`) |
| queue | a deque in memory | shared-memory queue (`boost::interprocess::message_queue`) |
| request / result | passed as objects | JSON files in `/tmp/tt-video-ipc-<server pid>/` |
| cancel of a queued job | taken out of the deque; no marker file | a `cancel-<id>` marker file the worker checks |
| runner crash (segfault) | takes the server down | the service fails and the server exits |
| warmup timeout | none (a hung warmup is not killed) | `WARMUP_TIMEOUT_MS` / weights distribution timeout |

Only the number of `DEVICE_IDS` groups decides the mode; there is no variable for it. A
multihost launch has one group (rank 0 serves HTTP), so it also runs in process; that
combination has not been run on several hosts. A Python exception in the runner is
caught in both modes and fails only that job. Everything below describes the worker
process mode unless it says otherwise; the API, statuses, limits, sweeper and output
directory work the same in both.

## How it works

Worker process mode:

```
client --HTTP--> server (Drogon) --shm queue--> worker (owns the device)
                   |                               |
            in-memory job table              generates the mp4 on disk
                   ^                               |
                   +------ shm result queue <------+
```

- The **server** validates the request, records a job (in memory) and puts a task
  into a shared-memory queue. It never generates video and never blocks an HTTP
  thread on generation.
- A **worker** is a separate process (`fork` + `execv`, `--worker <i>`). It loads
  the model once (warmup), takes tasks one at a time, runs the runner, and
  reports the result back through a per-worker result queue.
- The request body is passed to the worker as a small JSON file in
  `/tmp/tt-video-ipc-<server pid>/`; only ids and paths travel through the queue.
- The finished mp4 is written to `TT_VIDEO_OUTPUT_DIR`. The worker makes it
  *faststart* once (skipped if it already is), so it can be streamed and seeked.
- A background thread removes expired jobs and fails jobs that made no progress for
  too long.

In process mode there is no shm queue and no second process: the server keeps the
waiting tasks in a deque and one runner thread takes them one at a time (the same
runner factory as a worker process uses, so the model code is the same). The thread
sets the environment a worker process would get (`TT_VISIBLE_DEVICES`,
`OMP_NUM_THREADS`, `TT_METAL_CACHE`, ...) before it warms the runner up, and the
embedded Python interpreter does not install its own signal handlers, so SIGINT and
SIGTERM still reach the server.

## Running

Build as for the rest of `cpp_server` (see [AGENTS.md](../AGENTS.md)), then start the
binary with the video service selected.

Real device (T3K, Wan2.2):

```bash
source <tt-metal>/python_env/bin/activate
MODEL_SERVICE=video \
MODEL=Wan2.2-T2V-A14B-Diffusers \
MODEL_RUNNER=tt-wan2.2 \
DEVICE=t3k \
DEVICE_IDS="(0,1,2,3)" \
TT_DIT_CACHE_DIR=<path to the tt_dit weight cache> \
TT_METAL_HOME=<tt-metal> \
TT_VIDEO_TRACED=0 \
HF_HUB_OFFLINE=1 \
OPENAI_API_KEY=<token> \
./build/tt_media_server_cpp -p 8000
```

`DEVICE_IDS="(0,1,2,3)"` and `MODEL` are required on a T3K. The worker runs the model
through C++ classes (`src/runtime/dit/`, see [Models](#models)); the only Python is the
adapter of the model in `python/cpp_dit_adapters`, which calls tt-metal's `tt_dit`.
Nothing from the Python `tt-media-server` is loaded, so `TT_PYTHON_PATH` is not used.
`TT_VIDEO_PYTHON_DIR` points at another copy of the adapters (default
`cpp_server/python`). Details and troubleshooting (chip reset,
tracing) are in [tests/video/real_device/README.md](../tests/video/real_device/README.md).

Mock runner (no device, for development and CI-style checks):
[tests/video/mock/README.md](../tests/video/mock/README.md).

While the model warms up (can take minutes) `POST` returns `503` with
`Retry-After: 30`, and `/tt-liveness` reports `model_ready=false`.

## Models

`MODEL_RUNNER` selects the model. `src/runtime/dit/` is the C++ server's version of the
Python server's `tt_model_runners/dit_runners.py` for **Wan2.2 text-to-video and
image-to-video**, the two models that have been run on a device. The other runners of
that file (the Wan2.2 fine-tunes, Mochi-1, LTX-2.3, MiniMax-H3, the image models) are
not served by this server yet; they are kept on a working branch and will follow once
they are tested. The values (mesh shapes, fabric, trace regions, pipeline arguments,
mp4 encoding) are copied by hand from the Python server; a test compares the mesh
table with the Python server's config.

What is C++ and what is Python:

| | |
|---|---|
| C++ (`src/runtime/dit/`) | the model classes (`DiTModel`, `WanModel`, `WanI2VModel`), the registry, the mesh and fabric parameters, opening and closing the mesh through ttnn, request parsing and validation, the arguments of each pipeline call, warmup, the ffmpeg encoding (mp4, and mp4 with AAC sound) |
| Python (`python/cpp_dit_adapters/`) | per model a function that builds the `tt_dit` pipeline and one that calls it. Nothing else: no validation, no export, no configuration |

The pipelines themselves (`WanPipeline`, `WanPipelineI2V`) exist only in Python, in
tt-metal.

| `MODEL_RUNNER` | Input | `DEVICE` |
|---|---|---|
| `tt-wan2.2` | text | n150, t3k, galaxy, bh-galaxy, p150x4, p150x8, p300x2, galaxy_quad |
| `tt-wan2.2-i2v` | text + `image_prompts` | as `tt-wan2.2`, without n150 |

Any other `MODEL_RUNNER` is refused at start with the list of the supported ones.

Request fields beyond the text-to-video ones, on the same `POST /v1/videos/generations`:

- `image_prompts`: `[{"image": "<base64>", "frame_pos": 0}, ...]`, 1 to 81 entries,
  `frame_pos` in [-1, 81), each frame once. Required by the I2V models.
- `references`: `{"images": [{"b64": ...}], "videos": [...], "audios": [...]}`. Parsed
  and checked, but no model served here uses them yet (Ref2VA).
- Media must be inline base64; `url` sources are refused (the Python server downloads
  them). The job record (`GET`) shows only `frame_pos` and the reference counts, not
  the base64.

Model-specific limits are checked by the runner; a request it refuses fails as a job
with the runner's message.

To add a model: write a `DiTModel` subclass (or a subclass of `WanModel`) in
`src/runtime/dit/`: pass a `ModelSpec` (mesh per `DEVICE`, checkpoint, defaults), and
implement `adapterName()`, `adapterOptions()` and `buildCall()`; override
`deviceParams()` or `validate()` where the model differs. Add one row to
`src/runtime/dit/dit_registry.cpp` and, in `python/cpp_dit_adapters/`, an adapter
registered with `@register("<name>")` that builds the pipeline and calls it. Mesh
selection, warmup and export come from the shared code.
Tests: `build/dit_runner_test` (C++) and `tests/video/python` (adapters).

## Trying it with curl

Every route of the API as a copyable command. Set three variables once (port 8000,
the token is `OPENAI_API_KEY`); `jq` is optional, it only pulls the id out of the JSON.

```bash
export URL=http://localhost:8000
export TOKEN=<token>
export ID=<job id>   # set by the create command below, or paste an id from the job list
```

**Is the model ready?** No token needed; `"model_ready": true` after warmup (until
then `POST` returns `503`):

```bash
curl -s $URL/tt-liveness
```

**Create a job** (`POST /v1/videos/generations`, `202`). This one also stores the id
in `ID`:

```bash
ID=$(curl -s -X POST $URL/v1/videos/generations \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"prompt": "a red fox running through snow", "num_inference_steps": 20}' | jq -r .id)
echo $ID
```

Without `jq` the id is in the response body; copy it into `ID` by hand:

```bash
curl -s -X POST $URL/v1/videos/generations \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"prompt": "a red fox running through snow"}'
```

**Create with all optional fields** (the runner decides which values it accepts):

```bash
curl -s -X POST $URL/v1/videos/generations \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"prompt": "a red fox running through snow", "negative_prompt": "blurry", "num_inference_steps": 20, "seed": 42, "height": 480, "width": 832, "num_frames": 81, "fps": 16}'
```

**Job status** (`GET /v1/videos/generations/{id}`): `queued`, `in_progress`, then
`completed`:

```bash
curl -s $URL/v1/videos/generations/$ID -H "Authorization: Bearer $TOKEN"
```

**Wait until the job is finished** (polls every 5 s, prints the final status):

```bash
until curl -s $URL/v1/videos/generations/$ID -H "Authorization: Bearer $TOKEN" \
  | jq -e '.status | IN("completed","failed","cancelled")' >/dev/null; do sleep 5; done
curl -s $URL/v1/videos/generations/$ID -H "Authorization: Bearer $TOKEN" | jq .status
```

**List all jobs** (`GET /v1/videos/jobs`):

```bash
curl -s $URL/v1/videos/jobs -H "Authorization: Bearer $TOKEN"
```

**Download the mp4** (`GET /v1/videos/generations/{id}/download`, only when the job
is `completed`):

```bash
curl -s $URL/v1/videos/generations/$ID/download \
  -H "Authorization: Bearer $TOKEN" -o fox.mp4
```

**Download a byte range** (`206`; `416` if the range is past the end of the file):

```bash
curl -s $URL/v1/videos/generations/$ID/download \
  -H "Authorization: Bearer $TOKEN" -H "Range: bytes=0-1023" -o part.bin
```

**Cancel** (`POST /v1/videos/generations/{id}/cancel`; a queued job at once, a running
one after its generation ends):

```bash
curl -s -X POST $URL/v1/videos/generations/$ID/cancel -H "Authorization: Bearer $TOKEN"
```

**Delete** a finished job and its mp4 (`DELETE`; `409` while the job is still active):

```bash
curl -s -X DELETE $URL/v1/videos/generations/$ID -H "Authorization: Bearer $TOKEN"
```

**Synchronous request:** the response is the mp4 itself and no job is created. It stays
open until the video is ready (minutes on a device), so set no client timeout:

```bash
curl -X POST "$URL/v1/videos/generations?async=false" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"prompt": "a red fox running through snow"}' -o fox.mp4
```

The same with the JSON field instead of the query: add `"async": false` to the body.

## Browser console

With `MODEL_SERVICE=video` the server also serves a small web page at
`http://localhost:8000/` (and `/ui`). It needs no internet access and no extra build
step. Enter the API key at the top, then:

- send a request from a form (async or sync, all request fields);
- see all jobs on the server (auto-refreshing) and run status, download, `Range`,
  cancel and delete on a job with one click;
- run a ready-made request for every route and for the expected errors
  (`401`, `404`, `416`, `422`);
- run the full flow (create, wait, download, `Range`, delete, check `404`);
- see every request sent from the page with its response (a downloaded mp4 plays
  inline) and re-run it.

Every button has a small companion that copies the equivalent `curl`. The page
itself is served without a token; the API calls it makes still need the key. The
history is kept in the browser (`localStorage`), not on the server.

## API

All routes require `Authorization: Bearer <token>`.

| Method | Route | Purpose |
|---|---|---|
| `POST` | `/v1/videos/generations` | Create a job (`202`), or generate synchronously (see below) |
| `GET` | `/v1/videos/generations/{id}` | Job status |
| `GET` | `/v1/videos/jobs` | List all jobs |
| `GET` | `/v1/videos/generations/{id}/download` | Download the mp4 (`Range` supported) |
| `POST` | `/v1/videos/generations/{id}/cancel` | Cancel a job |
| `DELETE` | `/v1/videos/generations/{id}` | Delete a finished job and its mp4 |

`{id}` is the UUID returned when the job is created.

### Create

```json
{
  "prompt": "a red fox running through snow",
  "num_inference_steps": 20
}
```

Accepted fields: `prompt` (required), `negative_prompt`, `num_inference_steps`
(4 to 50, default 20), `seed`, `aspect_ratio`, `height`, `width`, `fps`,
`duration`, `num_frames`. The API does not validate resolution, frame count or
aspect ratio per model; that is left to the Python runner in the worker. A value the
runner rejects shows up as a `failed` job, not as a `4xx` on `POST`; a value it
ignores is simply accepted (for example an unknown `aspect_ratio` still produces a
video).

Mode: asynchronous by default (`USE_ASYNC_VIDEO`). Override per request with
`?async=true|false` or a JSON field `async`; any other value is `422`.
A synchronous request returns the mp4 itself (`Content-Type: video/mp4`,
`X-Generation-Time`) and creates **no job record**.

### Job object

```json
{
  "id": "6f1c1c0e-...",
  "job_type": "video",
  "status": "queued",
  "created_at": 1763100000,
  "model": "<served model name>",
  "request_parameters": { "...": "..." },
  "completed_at": 1763100080,
  "error": { "code": "processing_error", "message": "..." }
}
```

`completed_at` is present once the job is terminal, `error` only for `failed` jobs.

### Statuses

| Status | Meaning |
|---|---|
| `queued` | Accepted, waiting for a worker |
| `in_progress` | A worker is generating |
| `completed` | Done; the mp4 can be downloaded |
| `failed` | `error.code` is `processing_error` (worker error, worker crash, shutdown) or `stale_job` (no progress for `JOB_MAX_STUCK_TIME_SECONDS`) |
| `cancelling` | Cancelled while running; becomes `cancelled` when the worker returns |
| `cancelled` | Cancelled; its result is discarded |

Terminal statuses are `completed`, `failed`, `cancelled`.

### Cancel and delete

- Cancel of a `queued` job: immediately `cancelled`; the worker skips the task and
  the device is not used.
- Cancel of a running job: `cancelling`. The device cannot be interrupted, so the
  generation runs to the end, then the job becomes `cancelled` and the mp4 is deleted.
- Cancel of an unknown or already finished job: `404`.
- Delete of an active job: `409`. Cancel it first and delete once it is terminal.

### Download

`404` unknown job, `409` job not `completed` (the body carries the status, so a
client knows to keep polling), `404` completed job whose file is missing.
A single `Range: bytes=...` is honoured (`206`, `Content-Range`); an unsatisfiable
range is `416`. `Accept-Ranges: bytes` is always sent.

### Errors

Errors have the FastAPI-style `detail` and an OpenAI-style `error` object:

```json
{ "detail": "...", "error": { "message": "...", "type": "...", "param": null, "code": null } }
```

| Status | When |
|---|---|
| `401` | Missing or wrong bearer token |
| `404` | Unknown id, cancel of a finished job, download without a file |
| `409` | Delete of an active job, download of a job that is not completed |
| `416` | Unsatisfiable `Range` |
| `422` | Invalid JSON or field, `num_inference_steps` out of range, invalid `async` |
| `429` | Too many active jobs (`MAX_QUEUE_SIZE`); `Retry-After: 60` |
| `503` | Model warming up (`Retry-After: 30`), job table full (`MAX_JOBS`, `Retry-After: 60`), output directory not writable, service failed |

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `MAX_QUEUE_SIZE` | 1000 | Maximum active jobs before `429` (the default of every service of this server; the Python server's is 5000) |
| `MAX_JOBS` | 10000 | Maximum stored job records before `503` |
| `JOB_RETENTION_SECONDS` | 86400 | How long a finished job (and its mp4) is kept |
| `JOB_CLEANUP_INTERVAL_SECONDS` | 300 | Cleanup pass interval; `<= 0` disables the thread |
| `JOB_MAX_STUCK_TIME_SECONDS` | 10800 | A running job with no progress for this long becomes `failed` (`stale_job`); `<= 0` disables |
| `TT_VIDEO_IN_PROCESS` | auto | `1` runner on a thread of the server, `0` worker process; auto = in process for one `DEVICE_IDS` group |
| `TT_VIDEO_OUTPUT_DIR` | `<binary dir>/../videos` | Where mp4 files are written |
| `TT_VIDEO_PURGE_ON_START` | on | `0` keeps the results of a previous run at start (see below) |
| `SERVED_MODEL_NAME` | `MODEL_WEIGHTS_PATH`, else the runner name (e.g. `tt-wan2.2`) | Value of `model` in the job |
| `USE_ASYNC_VIDEO` | async | Default mode when the request does not choose |

Test-only hooks (never set in production): `TT_VIDEO_MOCK_DELAY_MS`,
`TT_VIDEO_MOCK_WRITE_FILE`, `TT_VIDEO_MOCK_WARMUP_MS`,
`TT_MEDIA_TEST_PRECLAIM_DELAY_MS`, `TT_VIDEO_MOCK_CANARY_FAIL`,
`TT_VIDEO_MOCK_CANARY_DELAY_MS`.

## Canary monitor

A port of the Python server's `health_monitoring/canary_monitor.py`
(`services/canary_monitor.hpp`), in both execution modes. While no request is in
flight, the service sends a probe the same way requests go (worker mode: a task
with `FLAG_CANARY` on the shm queue; in process: a slot the runner thread takes
before its next task). The runner answers it with `healthCheck(deep)` instead
of running the model. Consecutive misses (timeout, error, false) move the state
`healthy` -> `suspect` -> `dead`; a real request in flight counts as proof of
life and clears the misses.

- **Shallow probe:** the worker loop or the runner thread takes work.
- **Deep probe** (every Nth probe, off by default): also a small computation on
  every chip of the mesh, read back and checked on the host
  (`python/cpp_dit_adapters/device_check.py`: each chip doubles its own tile,
  with new values on every probe). It does not use the links between chips. A
  hung device does not answer and the probe times out.
- Misses are counted per depth, so a passing shallow probe does not hide a
  failing deep one; `suspect` and `dead` stay visible while the next probe runs.
- At most one probe is on the queue; one that timed out is waited for again on
  the next tick. The shm task queue has one extra slot for it.
- `/tt-liveness` adds `canary_alive` and `canary_state`. With
  `CANARY_GATE_READINESS=1`, a `dead` monitor makes `/tt-liveness` and `/health`
  answer `503 {"detail": "Canary monitor: model not serving"}`.
- Metrics: `tt_canary_state`, `tt_canary_failures_total`,
  `tt_canary_probe_latency_seconds`, `tt_canary_last_success_timestamp` (the
  Python names and labels).

| Variable | Default | Meaning |
|---|---|---|
| `CANARY_ENABLED` | true | Run the monitor (`canary_state` is `disabled` otherwise) |
| `CANARY_GATE_READINESS` | false | A `dead` monitor answers `503` on `/tt-liveness` and `/health` |
| `CANARY_WAIT_SECONDS` | 5 | Idle time before a probe |
| `CANARY_PROBE_TIMEOUT_SECONDS` | 3 | Deadline of a shallow probe |
| `CANARY_TICK_SECONDS` | 1 | Monitor loop period |
| `CANARY_DEAD_MISSES` | 3 | Consecutive misses before `dead` |
| `CANARY_STARTUP_GRACE_SECONDS` | 30 | No probe for this long after the service is ready |
| `CANARY_DEEP_PROBE_ENABLED` | false | Send deep probes |
| `CANARY_DEEP_EVERY_N` | 3 | Every Nth probe is deep |
| `CANARY_DEEP_PROBE_TIMEOUT_SECONDS` | 60 | Deadline of a deep probe (the first one compiles the kernel) |

## Behaviour to be aware of

- **Jobs live in memory only.** A server restart drops every job record.
- **Startup purge.** With a real device runner, the server deletes the results of a
  previous run directly inside `TT_VIDEO_OUTPUT_DIR` at start (files named
  `<uuid>.mp4`, `<uuid>_silent.mp4`), because after a restart none of them has a
  record. This includes finished videos. Other files, including other `*.mp4`, are
  never touched. Each server keeps a lock on `.tt_video_server.lock` in the folder
  while it runs; a server that finds the lock held by another one skips the purge
  and logs a warning, so two servers can share a folder. `TT_VIDEO_PURGE_ON_START=0`
  turns the purge off.
- **Synchronous requests** (`?async=false`) have no job record: the mp4 is read into
  the response and deleted at once, so the whole video is held in memory while it
  is sent.
- **Deletion is confined** to `TT_VIDEO_OUTPUT_DIR`: a result path outside it is
  never deleted (`..` and symlinks are resolved first).
- **A stuck job is only marked failed.** The worker process is not interrupted; if
  its result arrives later it is discarded and its mp4 removed.
- **Worker crash.** A dead worker is not restarted: the service is marked failed, the
  jobs it held or that were still waiting become `failed`, and the process exits with
  code 1, so it needs a supervisor (systemd, container restart policy) to come back.
- **In process mode: crash and shutdown.** A Python exception fails only its job. A
  crash of the native code (a segfault in tt-metal) takes the whole server down and
  nothing restarts it, so it needs a supervisor, and on a T3K the chips need
  `tt-smi -r` first. SIGTERM of an idle server exits at once (code 0); during a
  generation the server waits 10 s for it (a generation cannot be interrupted), then
  exits with code 1 without closing the device, so the next start needs
  `tt-smi -r`. `tt_video_server_overhead_seconds{phase="request_write"|"shm_enqueue"}`
  has no samples in this mode (there is no request file and no shm queue).
- **Shutdown.** SIGTERM of an idle server exits cleanly (code 0, no worker left, the
  ipc folder and shm queues are removed) and the next start works at once. SIGTERM
  while a job is running closes the device under the generation and exits in under a
  second; the next start then needs `tt-smi -r` on a T3K. Let the running job finish
  (or cancel it and wait) before stopping the server.
- **Routes with a path parameter** must be registered both in `VideoController` and
  in `registerVideo()` (as `{job_id}`); see the comment above `METHOD_LIST_BEGIN` in
  `include/api/video_controller.hpp`.

## Differences from the Python server

Observed with the same requests against both servers on a T3K (the routes, status
codes, error cases and the `Range` behaviour are the same):

| | Python server | This server |
|---|---|---|
| error body | `{"detail": ...}` | `{"detail": ..., "error": {...}}` |
| `model` in the job | the weights name (`Wan-AI/Wan2.2-T2V-A14B-Diffusers`) | `SERVED_MODEL_NAME`, else `MODEL_WEIGHTS_PATH`, else the runner name |
| `download` of an unfinished job | `404` | `409` |
| `ETag`, `Last-Modified` on `download` | sent | not sent (`If-Range` is not usable) |
| `HEAD` on `download` | `405` | `200` |
| `?async=false` | ignored (the server setting decides) | supported, and `?async=banana` is `422` |
| default `MAX_QUEUE_SIZE` | 5000 | 1000 (set `MAX_QUEUE_SIZE=5000` for the same limit) |
| worker crash on a device | the held job stays `in_progress`, liveness `503`, the process keeps running | the held job becomes `failed`, the process exits with code 1 |


## Known limitations

- Text-to-video only: no image-to-video, reference-to-video or media upload.
- No `org_id` filtering in the API, no per-step progress, no metrics/logs/checkpoints routes.
- `GET /v1/videos/jobs` returns every job, without pagination or filters.
- A running generation cannot be interrupted (cancel waits for the end of the run).
- **Worker crash on a device needs a chip reset.** The job it held becomes `failed` and
  the server exits with code 1 (there is no automatic restart). The chips cannot be
  opened again without `tt-smi -r`: reset them and start the server again.
- Worker process mode: a worker that is **idle** (waiting in the shared task queue) and is
  killed with `SIGKILL` can leave the queue's process-shared condition variable in a state
  that blocks the next `POST` for good (the HTTP thread sits in `pthread_cond_signal` inside
  `message_queue::send`; the server keeps running but stops answering). Reproduced on the
  mock runner with two groups, with the current and with the pre-in-process binary, so it
  is not caused by in process mode. A worker killed while it runs a job does not trigger
  it (the tests kill busy workers). A fix means not waiting on the shared condition
  variable in the workers (poll) or a robust synchronisation primitive.
- When `TT_VIDEO_OUTPUT_DIR` cannot be written (missing and not creatable, read-only,
  full), `POST` (async and sync) is refused with `503` before any device time is spent;
  the server logs an error at start and checks again on every request, so fixing the
  folder is enough, no restart. A disk that fills up in the middle of a generation can
  still fail that one job.
- Orphan `/tmp/tt-video-ipc-<pid>` folders of killed servers are not removed.
- A stuck-job sweep against a real device hang, a full disk, and several workers are
  not tested on a device.
- On a T3K, Wan2.2 (T2V and I2V) runs untraced by default: with tracing the output
  is noise. Other devices keep the Python server's default (traced);
  `TT_VIDEO_TRACED=1` turns tracing on explicitly, `0` turns it off.
- Only `tt-wan2.2` (text-to-video) has run on a device through this server;
  `tt-wan2.2-i2v` is covered by device-free tests of its pipeline arguments (C++)
  and adapter (a fake pipeline).
- No `/v1/videos/generations/i2v/upload` (multipart) and no media URL download: images
  and references are sent as base64 in the JSON body.
