# QB2 CI runners need quarantine and health checks

During Gemma 4 31B agentic evaluations on 9–10 October 2026, the shared `bh-qb-ge` pool assigned jobs to hosts where setup failed before evaluation. The same inference-server commits and pinned Metal image ran on other hosts. This establishes runner-associated failures, not a proven hardware root cause.

| Runner | Failed here | Worked elsewhere |
| --- | --- | --- |
| `p04t07` | [Terminal job](https://github.com/tenstorrent/tt-agentic-bringup-qb2/actions/runs/37962790734): a stopped, unowned Docker container caused Shield to refuse cleanup and hardware execution. | [Same model commit/image, Terminal five](https://github.com/tenstorrent/tt-agentic-bringup-qb2/actions/runs/37963842946) completed on `p05t02` after a separate TB2.0 workflow allowlist fix. |
| `p04t05` | [C8 Terminal job](https://github.com/tenstorrent/tt-agentic-bringup-qb2/actions/runs/38001414052): four-chip fabric mapping failed at `topology_mapper.cpp:556`. This host also emitted [800 MHz versus 1350 MHz AICLK warnings](https://github.com/tenstorrent/tt-agentic-bringup-qb2/actions/runs/37963243142). | [Same C8 model commit/image and ten cases](https://github.com/tenstorrent/tt-agentic-bringup-qb2/actions/runs/38010947583) completed on `p05t05` (wrapper added hold jobs). This host had itself completed C8 SWE earlier, so the failure was not constant. |
| `p05t06` | [C4/eight-agent Terminal job](https://github.com/tenstorrent/tt-agentic-bringup-qb2/actions/runs/38043892436): the same fabric mapping error after this host had completed other Gemma work. | [Same model and wrapper commits, image and twenty cases](https://github.com/tenstorrent/tt-agentic-bringup-qb2/actions/runs/38048296731) completed on `p05t05`. |

To keep long evaluation jobs off these hosts, I added temporary [`hold-*` jobs](https://github.com/tenstorrent/tt-agentic-bringup-qb2/blob/mvasiljevic/gemma-tb2-ci/.github/workflows/manual-tt-shield-dispatch.yml). They occupy an affected runner for up to 170 minutes, checking either for existing containers or an exact runner name. The hold steps do not remove containers or reset devices. This required manual assignment checks, repeated dispatches, and renewals as holds expired; several model jobs were canceled before hardware work and reissued on other hosts.

**Requested:** Resolve ownership of the container on `p04t07`; check four-chip fabric connectivity and topology discovery on `p04t05` and `p05t06`; investigate the 800 MHz AICLK warning; and provide a maintained quarantine or health label so affected runners can be excluded without sleeping Actions jobs. The fabric failures could reflect intermittent host state or a host-sensitive software/discovery issue; these comparisons do not prove defective hardware.
